# P2 Dashboard Enhancement 需求

执行依据：用户已确认原 P2-01 至 P2-06 路线及评估中的调整，要求各阶段合入同一个 PR。

## 范围与约束

保持 `scripts/dashboard` 生成、`.pair/dashboard` 输出、纯静态 HTML、本地资源、无前端构建链。
Dashboard 只读源状态；工作流负责会话元数据，生成器不创建或修改 `.pair` 源记录。
沿用已确认的 P2-01 视觉系统。统一更新现有 PR #7；不自动合并。

## 验收标准

1. 当展示项目时，应并列显示工作流阶段、步骤完成比例、记录的验证结果和知识覆盖；缺失数据保持未知。
2. 当设计待批准、恢复异常或存在未完成 takeover 时，应突出处理原因和建议的 `/pair` 命令。建议不执行命令。
3. 当展示步骤依赖时，应从 `manifest.steps.dependencies` 读取边、从 `progress.steps` 读取执行状态；应检测重复 ID、缺失依赖和环。
4. 当步骤依赖未完成时，应计算独立的 readiness/blocked_by，保持源 status。被 skipped/superseded 的依赖不自动视为已实现。
5. 当统计实现来源时，应按已完成步骤的 `human / ai / mixed / unknown` 展示数量、比例、分母和记录覆盖率；不推测 mixed 的拆分比例。
6. 当读取会话时，应支持带 YAML frontmatter 的 Markdown、YAML/JSON 元数据及既有纯 Markdown；真实起止时间只取明确记录，旧记录保持时间/结果未知。
7. 当导出历史时，应使用稳定会话 ID，生成可从源记录重建的 JSON；同一天多个会话不覆盖，重复 ID 明确报错，源记录删除时清理对应的受管理产物。
8. 当 Watch 检测输入变化时，应重新生成并输出步骤变化；不监控自身产物。无效输入保留上一份有效业务数据并显示 stale/错误状态，恢复后清除。
9. 当使用 `--workspace` 时，应只扫描直接子目录的 `.pair`，跳过隐藏目录、依赖目录和符号链接；单项目读取失败不影响其他项目，错误项目不显示伪造百分比。
10. 当使用 workspace Watch 时，应检测项目新增/删除及所有已消费的状态源，包括 sessions 和 operations。
11. 当使用 JSON-only 时，应只生成 JSON 产物（含 history），保留现有 HTML/资源。命令、安装包和文档应覆盖所有新入口。
12. 自动化测试应覆盖图与指标语义、旧记录兼容、历史重建、故障隔离、Watch 重试/退出及安装后入口；浏览器应检查深浅色、手机布局和资源导航。
